# Аудит проекта TachTachAI (29 марта 2026)

## Краткая оценка

Проект выглядит как **MVP-фреймворк для UI-автоматизации и сценарного тестирования** с тремя уровнями:
1. исполнитель действий (`smart_cursor.py`),
2. раннер сценариев (`test_runner.py`),
3. управляющий контур/оркестратор (`command_interface.py`).

На текущем этапе ключевые проблемы связаны с:
- сильной привязкой к GUI/Windows окружению,
- неполной реализацией части действий,
- смешением интерактивного и CI-режима,
- отсутствием строгой схемы валидации сценариев,
- нестабильностью запуска тестов в headless/Linux среде.

## Что уже работает (функционал)

- Сценарный запуск тестов и шаговое выполнение действий через `subprocess` на `smart_cursor.py`.
- Диагностика при падении шага: системные метрики, сетевой чек и серия скриншотов.
- Примитивный перформанс-трекинг шагов с baseline и детекцией регрессии.
- Data-driven режим через CSV-подстановку в шаги сценария.
- Режим командного интерфейса с чтением рекомендаций/инструкций из JSON-файлов.

## Основные проблемы

### 1) Непереносимость и падения в non-GUI среде

- `pyautogui` импортируется на уровне модуля в `diagnostics.py` и `smart_cursor.py`. В headless окружениях это приводит к ошибкам уже на этапе импорта (например, отсутствие `DISPLAY`).
- UIA-ветка ориентирована на Windows (`pywinauto`, win32-компоненты), но тесты и часть модулей не изолированы от Linux/CI.

**Риск:** тесты не проходят даже этап collection в обычном CI-контейнере, что блокирует QA-пайплайн.

### 2) Неполная реализация заявленных возможностей

В `smart_cursor.py` несколько ключевых OCR/Image действий возвращают заглушки `True` и не выполняют реальную работу:
- `find-image`
- `find-text`
- `assert-image`
- `assert-text`

**Риск:** ложноположительные результаты тестов и искаженная аналитика качества.

### 3) Несогласованность контрактов действий

- В `scenario_manager.py` интерактивный режим перечисляет действия (`type`, `wait-for-image`, `assert-visuals` и др.), которые фактически отсутствуют в `ACTION_HANDLERS` `smart_cursor.py`.
- Из-за этого можно записать сценарий, который гарантированно упадет при исполнении как «Unknown action».

**Риск:** высокий процент ложных сбоев из-за дефектов DSL/контракта, а не из-за продукта.

### 4) Ошибочный интерфейс для baseline performance

В `command_interface.py` команда `create_performance_baseline` вызывает `delete_performance_baseline(...)`, то есть вместо создания baseline выполняется удаление.

**Риск:** неочевидная потеря эталонов производительности и невозможность корректного regression tracking.

### 5) Блокирующая интерактивность в контуре оркестрации

`command_interface.py` в цикле ожидает `input("Execute these recommendations? (yes/no): ")`.

**Риск:** зависание в non-interactive средах, где стандартный ввод недоступен (CI, daemon, cron).

### 6) Недостаточная валидация входных данных сценариев

- Сценарии загружаются как JSON без схемы и без строгой проверки полей/типов.
- В рантайме часть ошибок гасится (например, пропуск KeyError при подстановке placeholder), что затрудняет диагностику качества тест-данных.

**Риск:** дефекты в сценариях обнаруживаются поздно и непредсказуемо.

## Результат быстрой технической проверки

Запуск `pytest -q` в текущем окружении завершился ошибками collection из-за зависимостей GUI/Windows (`DISPLAY`, `win32process`, `pywinauto` import path).

Это подтверждает, что проект в текущем виде ориентирован на узкое исполняющее окружение и требует явного разделения:
- unit-тесты (кроссплатформенные, без GUI),
- интеграционные UI-тесты (только Windows/GUI runner).

## Приоритетный план стабилизации

1. **P0: Сделать безопасный импорт GUI-зависимостей** (ленивый импорт внутри функций + graceful fallback).
2. **P0: Починить контракт baseline-команды** (`create` не должен вызывать `delete`).
3. **P0: Сверить DSL действий** между `scenario_manager.py` и `smart_cursor.py`.
4. **P1: Ввести JSON Schema/Pydantic-валидацию** для сценариев и команд.
5. **P1: Разделить профили запуска тестов** (unit vs ui-e2e) с маркерами pytest.
6. **P2: Реализовать реальные OCR/Image проверки** вместо заглушек.

## Итоговая оценка

- **Идея и архитектурный скелет:** хорошие для MVP.
- **Операционная готовность:** низкая в универсальном CI, средняя в специально подготовленном Windows+GUI окружении.
- **Главный ограничитель ценности сейчас:** технический долг вокруг платформенной зависимости и неполных экшенов.
