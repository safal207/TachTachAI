# TachTachAI — план выхода в production

Дата: 30 марта 2026

## Цель
Собрать стабильную **production-версию** с предсказуемым запуском, воспроизводимыми тестами и понятным SLA для автоматизации.

## 0) Freeze MVP и границы v1

**Что фиксируем в v1:**
- Один движок по умолчанию (`SMART_CURSOR_ENGINE=uia`),
- Сценарии только из поддерживаемого DSL,
- Надежный `command_interface` (статус, базовые команды, отчеты),
- CI без падений collection.

**Критерий готовности шага:** scope v1 зафиксирован документом + чеклистом.

---

## 1) Стабильность ядра (P0)

1. Убрать placeholder-экшены OCR (`find-image/find-text/assert-*`) или пометить как experimental и исключить из production-профиля.
2. Ввести строгую валидацию сценариев (JSON Schema/Pydantic):
   - обязательные поля,
   - типы,
   - совместимость с выбранным engine.
3. Стандартизировать коды ошибок и формат ответа команд (`status/error/data`).
4. Сделать idempotent поведение baseline-команд (`create/update/delete`) и unit-тесты на файловые операции.

**DoD:** 100% unit pass по core-модулям, ноль runtime-crash на невалидном входе.

---

## 2) Production-конфигурация и профили запуска (P0)

1. Ввести профили окружений:
   - `dev`,
   - `ci`,
   - `prod-agent`.
2. Вынести конфиг в `.env`/`config.yaml`:
   - engine,
   - timeouts,
   - retry policy,
   - директории отчетов/артефактов.
3. Запретить интерактивность в prod/ci (без `input()`-блокировок).

**DoD:** запуск в CI и prod без ручного ввода, deterministic конфигурация.

---

## 3) Тестовая стратегия (P0/P1)

1. Разделить тесты маркерами:
   - `unit` (кроссплатформенные),
   - `integration` (локальные зависимости),
   - `e2e_ui_windows` (GUI/Windows).
2. В CI по умолчанию гонять `unit + integration`.
3. `e2e_ui_windows` запускать отдельным Windows-runner пайплайном по расписанию.
4. Добавить coverage gate для core (например, >=80%).

**DoD:** стабильный green CI минимум 20 прогонов подряд.

---

## 4) Наблюдаемость и эксплуатация (P1)

1. Перевести логирование на structured JSON logs.
2. Добавить correlation_id/run_id для каждого запуска.
3. Метрики:
   - success/failure rate,
   - средняя длительность шага,
   - количество retriable/non-retriable ошибок.
4. Ротация отчетов и артефактов + лимиты хранения.

**DoD:** из логов можно восстановить полный ход любого падения за 5 минут.

---

## 5) Надежность исполнения (P1)

1. Retry policy по классам ошибок (network/transient/ui-timeout).
2. Circuit-breaker для нестабильных внешних зависимостей.
3. Таймауты на каждый шаг + глобальный watchdog на сценарий.
4. Graceful shutdown и cleanup процессов (особенно Windows UI apps).

**DoD:** снижение flaky-failure минимум на 50% относительно текущего baseline.

---

## 6) Безопасность и supply chain (P1)

1. Pin зависимостей (lockfile), регулярный security scan.
2. Минимально необходимые права запуска.
3. Санитизация внешних входных данных (CSV/JSON/команды).
4. Подготовить threat model v1.

**DoD:** нет критических уязвимостей в зависимостях на релизе.

---

## 7) Релизный процесс (P1/P2)

1. Semantic versioning + changelog.
2. Release checklist:
   - тесты,
   - миграции,
   - обратная совместимость DSL,
   - rollback plan.
3. Канареечный rollout для production-агентов.

**DoD:** воспроизводимый релиз за <=30 минут.

---

## 8) Коммерческая production-версия (P2)

1. API-слой над командами (REST/gRPC) вместо файлового обмена.
2. RBAC/мульти-tenant модель.
3. Планировщик очередей заданий и приоритетов.
4. Web dashboard (живой статус, история прогонов, алерты).

**DoD:** multi-tenant эксплуатация и горизонтальное масштабирование.

---

## Предлагаемый порядок работ (на 6 недель)

### Недели 1–2
- P0 стабильность ядра,
- P0 профили окружений,
- разметка тестов.

### Недели 3–4
- Observability,
- retry/watchdog,
- windows e2e pipeline.

### Недели 5–6
- релизный процесс,
- API-обертка,
- подготовка v1.0.0-rc.

## Критерии «готово к production»

- Green CI: 20/20 запусков,
- Нет критических багов P0,
- Есть rollback playbook,
- Есть мониторинг + алерты,
- Документация для on-call и операционного запуска завершена.
